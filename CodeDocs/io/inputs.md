# io/inputs — formats the code consumes

Update this whenever a consumed format changes (Rule 3).

| Input | Location | Format | Notes |
|-------|----------|--------|-------|
| Sample footage | `dataset/raw-video/*.mp4` (gitignored) | video container | ~370 MB, ~1 h each. **Never opened directly** — only via the Stage 0 frame-selection stage. **Active consumer: `frame_select.py`** (`select_frames` / `iter_selected_frames`), a **dev/batch** decode — never on the REST runtime path. Both resolution **and fps** are read from the media at runtime (OpenCV `CAP_PROP_*`, ffprobe fallback), never assumed; the decode stride is derived from the measured fps. See `CodeDocs/sources/dbcv/frame_select.md`. |
| Live-recorded session footage | `dataset/live_<UTC>/` (gitignored) | mp4 (constant frame rate) + `frames.jsonl` + `session.json` sidecars | **New provenance (2026-07-29)** for `dataset/` video, produced by `utils/python/record_session.py` (continuous WGC recording of live gameplay, replacing reliance on the two sample videos). Same consumption path as the samples: Stage 0 `frame_select.py` stride-decodes the mp4; resolution/fps still read from the media at runtime. Extra affordance the samples lack: the stream is CFR at a recorded `target_fps` with `session.json` carrying `cfr_epoch_wall`, so a wall-clock action-log event maps to an encoded frame via `frame_index = round((wall_ts - cfr_epoch_wall) * target_fps)` (weak temporal labeling). `session.json` also records the game build version per the footage-version-drift rule. Segments (`session_seg2.mp4`, …) appear only if the window was resized mid-session. **Never open the mp4s directly** — same rule as the samples. |
| Selected frames | `dataset/frames/` (gitignored) | PNG image files | Output of frame selection; what all downstream stages actually see.  Named `<Set>_<NNN>_t<SSSSS>s.png`. |
| Video metadata sidecar | `dataset/raw-video/_video_meta.json` (gitignored with the videos) | JSON (list, one object per sample) | Small ffprobe-derived sidecar written by a scrap probe script: `file`, `width`, `height`, `codec`, `pix_fmt`, `fps`, `duration_s`, `nb_frames`, `size_mb` per sample. Reference for humans/agents so nobody opens the ~370 MB videos to answer metadata questions. **Doc/reference only — no code consumes it, and its values (currently 1920×1080 @ 60 fps) must never be baked into code**; runtime always measures from the media. |
| **API frame upload** | `POST /v1/snapshot` (multipart) | image bytes (PNG/JPEG/BMP/etc.) | **New in slice (2026-06-22).** The REST endpoint accepts any format that OpenCV (`cv2.imdecode`) can decode.  Resolution is read from the decoded `np.ndarray` — never assumed from the request. |
| Card-art gallery | `knowledge-base/card-art/<role_class>/<identity>/<file>.png` (gitignored) | PNG image files | **Active — Stage 2 (classical + embedding).** 67 PNGs across 43 townee identities. Consumed by both `build_gallery()` (HSV+ORB) and `build_embedding_gallery()` (ONNX embeddings) at server startup. In-memory only; never persisted. Classical gallery: art swap = replace PNGs + restart, zero gradient steps. Embedding gallery: art swap is best handled by re-fine-tuning the backbone first (see below), then rebuilding. See `CodeDocs/sources/dbcv/gallery.md`. |
| ONNX embedding backbone (served) | `models/mobilenetv3_small_embed.onnx` (gitignored via `*.onnx`) | ONNX model file | **Active — Stage 2 (embedding identifier).** MobileNetV3-Small, classifier head stripped, **domain-fine-tuned** on the 43 card characters (Proxy-Anchor LP-FT); input [N,3,224,224] float32; output [N,576] float32 (raw, L2-normalised at runtime). Generated by `utils/python/finetune_embedding.py` (dev-only, requires torch + GPU). Loaded once at startup by `OnnxEmbedder` via onnxruntime CPU provider. See `models/README.md` for regeneration. |
| ONNX embedding backbone (frozen baseline) | `models/mobilenetv3_small_embed_frozen.onnx` (gitignored) | ONNX model file | **Dev / comparison only — not loaded at runtime.** The frozen-ImageNet baseline kept for the fine-tune head-to-head. Same architecture and I/O contract as the served model. Generated by `utils/python/export_backbone.py`. See `models/README.md`. |
| Cached game facts | `knowledge-base/wiki/*.md` | markdown | Transcribed/transformed wiki content (roles, mechanics). The raw fetch cache (`wiki/_raw_cache/`) is gitignored. |
| Run config | `src/dbcv/config.py` via env vars | pydantic-settings / `.env` | `Settings` class with `DBCV_` prefix.  `frames_dir` defaults to `dataset/frames/` anchored to repo root.  No resolution baked in. |

## API frame upload — detail

Endpoint: `POST /v1/snapshot`

Accepted fields (multipart/form-data):
| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|-------|
| `file` | `UploadFile` (image bytes) | Yes | — | Any format `cv2.imdecode` supports |
| `video` | `str` (Form) | No | `"unknown"` | Source video stem (no path) |
| `frame_index` | `int` (Form) | No | `0` | Zero-based frame index |
| `timestamp_s` | `float` (Form) | No | `0.0` | Seconds from video start |

Resolution is read from the decoded image (`image_array.shape[:2]`) inside
`run_pipeline` — never passed as a request parameter and never assumed.

## Open contract questions

- Frame-selection output: the **in-memory** record now exists — `SelectedFrame`
  (`frame_index`, `timestamp_s`, `state`, `dhash`) from `frame_select.py` (see
  `outputs.md`). What is still undefined is the **on-disk** persistence format: the
  naming convention `<Set>_<NNN>_t<SSSSS>s.png` is observed in `dataset/frames/`, but
  no sidecar (JSON/CSV) mapping selected PNGs to their `SelectedFrame` metadata has
  been defined yet, and the batch runner that would write it is not yet promoted to
  `utils/python/`.
- Card-art gallery manifest format: the directory tree (`<role_class>/<identity>/<stem>.png`)
  is the implicit manifest. No explicit sidecar file exists yet. The `Gallery` object
  derived from it at runtime is the runtime manifest. An explicit JSON manifest for
  versioning purposes may be added later.
