## How to use

- **Append, don't rewrite.** If findings change, add a new dated entry that references the old one.
- **Cite the real source.** Prefer primary, recent, and authoritative material.
- **Rate trust honestly** using the rubric below.
- **The abstract reports what was found**, including null/negative results — not what we wished were true.

## Authority / trust rubric

| Tier | Meaning |
|------|---------|
| **A** | Peer-reviewed paper, official library/standard documentation, or a recognized authority (e.g. OpenCV docs, a maintainer, a benchmark paper). |
| **B** | Credible practitioner source with shown evidence (reproducible blog post with code/numbers, conference talk, well-known engineering blog). |
| **C** | Community/anecdotal (forum answer, single blog assertion, undated tutorial) — usable as a lead, not as proof. |
| **D** | Unverified / AI-generated / marketing — record only with a flag, verify before relying. |

## Live window capture + synthetic input for a running Windows game (Windows Graphics Capture vs DXGI/mss-GDI/OBS virtual cam; SendInput/pydirectinput vs pyautogui's legacy mouse_event) — 2026-07-29

- **Source:**
  - *Windows.Graphics.Capture namespace* — Microsoft Learn official API docs — https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture ; *Screen capture (Windows.Graphics.Capture)* overview — https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture
  - `windows-capture` (pip package, wraps WGC for Python; used here at **2.0.0**) — https://pypi.org/project/windows-capture/ ; https://github.com/NiiightmareXD/windows-capture
  - `DXcam` (DXGI Desktop Duplication-based capture) — https://github.com/ra1nty/DXcam — README documents it captures the **composited desktop**, not a single window
  - `mss` (python-mss, GDI/`BitBlt`-based cross-platform capture) — https://python-mss.readthedocs.io/
  - OBS Studio *Virtual Camera* guide — https://obsproject.com/kb/virtual-camera-guide
  - `pydirectinput` (used here at **1.0.4** — `SendInput` + scan codes, a fork purpose-built for games PyAutoGUI can't reach) — https://github.com/learncodebygaming/pydirectinput ; https://pypi.org/project/pydirectinput/
  - PyAutoGUI docs (confirms it drives the legacy `mouse_event`/`keybd_event` Win32 calls, not `SendInput`) — https://pyautogui.readthedocs.io/
  - *Setting the default process DPI awareness* / `SetProcessDpiAwareness` — Microsoft Learn — https://learn.microsoft.com/en-us/windows/win32/api/shellscalingapi/nf-shellscalingapi-setprocessdpiawareness
- **Authority / trust:** **A** for the Microsoft Learn API/DPI docs (official platform documentation). **B** for `windows-capture`, `DXcam`, `mss`, `pydirectinput`, and PyAutoGUI's own docs (maintainer-authored, technically accurate for their own library, not independently peer-reviewed). The empirical results below are **primary data from this session** — direct measurement on this machine, not literature — and are reported as such, not rated on the A–D rubric.
- **Reason for inclusion / what we were looking for:** Before touching a live, running game (as opposed to the recorded sample videos this repo has used exclusively so far), we needed a capture method that survives a real desktop (occluding windows, minimized/RDP sessions) and an input method the target game actually accepts, plus a documented reason to prefer each over the obvious first guess.
- **Abstract of findings:** Four capture families split on one axis — **what they capture and how they behave under occlusion.** **DXGI Desktop Duplication** (`DXcam` et al.) captures the **composited desktop output**, not an individual window; when the target window is covered, minimized, or off the active virtual desktop, output frames go stale/black — it is a desktop-mirror API, not a window API. **GDI `BitBlt`-style capture** (`mss`, plain `win32gui`) is CPU-bound and, per longstanding documented Windows behavior, does not reliably read back **GPU-composited / DirectX-rendered** surfaces (hardware-accelerated windows commonly `BitBlt` as black or stale) — unreliable against a game engine's swap chain. **OBS's virtual camera** works (game capture → OBS → virtual cam driver → any app that reads a webcam) but is a heavy external-process dependency with an extra encode/decode hop, adding latency and a second application to keep running — usable, but the wrong default for an unattended capture+control loop. **Windows Graphics Capture** (`Windows.Graphics.Capture`, Win10 1803+, refined 1903+) is explicitly **window-targeted** — you hand it an `HWND`/`GraphicsCaptureItem` — and is documented to keep producing frames even when the window is occluded by other windows, which is exactly the desktop-composited APIs' weak point; it returns BGRA frames via a frame pool. On input: PyAutoGUI's own docs confirm it drives the legacy `mouse_event`/`keybd_event` Win32 calls; many DirectX/fullscreen-exclusive-or-borderless games only react to input delivered through the newer **`SendInput`** API with hardware-style scan codes, which is why `pydirectinput` exists as a drop-in PyAutoGUI-compatible fork built specifically around `SendInput` + scan codes for games that ignore PyAutoGUI.
- **Empirical validation on this machine (Windows 11, *Demon Bluff* v0.762b, Unity IL2CPP, Steam appid 3803820, launch options `-popupwindow -screen-fullscreen 0`):** WGC (`windows-capture` 2.0.0) captured the windowed game at **1346×879 @ ~55–57 FPS**. Synthetic input via `pydirectinput`'s `SendInput`-based clicks **is accepted by this Unity build** — verified directly by diffing before/after frames across a real menu transition (menu → Pick Game Mode). The launcher path `steam://rungameid/3803820` plus polling for the game window works end to end. Capture **survives a minimized RDP client session** (the local screen can be locked/disconnected-from while the remote desktop keeps compositing) — confirming the window-targeted, occlusion-tolerant behavior documented above, on our own footage rather than just the vendor's claim.
- **Honest caveats (also the open risk list for the next session):** `-popupwindow` did **not** remove window chrome *on the first session's launch options* (`-popupwindow -screen-fullscreen 0` alone) — captured frames included the OS title bar. **Update, same day:** with the full flag set `-screen-width 1280 -screen-height 720 -popupwindow -screen-fullscreen 0`, the game launches **truly borderless at exactly 1280×720** (verified: WGC frame is edge-to-edge game pixels, no chrome, via both Steam's own launcher and the `steam://rungameid` script path) — the explicit width/height appears to keep the game's own windowed-mode re-apply from recreating the window with a border. This also makes live capture **geometrically congruent with the 16:9 training footage** (sample frames are 1280×720; the earlier chrome'd window was ~1.59:1 vs the samples' 1.778 — an aspect-ratio domain shift now eliminated at the source). Chrome-cropping via live `GetClientRect` remains the documented fallback if a future game update changes flag behavior. **Title-substring window matching is unsafe** — a File Explorer window merely *browsing the game's install folder* matched on the string "Demon Bluff"; window selection must also verify the owning process image is `Demon Bluff.exe`. A **minimized** game window gives stale WGC frames — minimized is an unsupported capture state, distinct from occluded-but-not-minimized (which works). The in-game **Brightness slider is an untested domain-shift risk**: all frames captured so far are at default brightness, so any trained recognition stage's generalization to other brightness settings is unmeasured. Card hit-boxes extend beyond the visible card art (matters for click-target accuracy, not just visual bounding boxes). The bottom-right action-icon row is **not positionally stable** across game states — cannot be treated as a fixed click target. A **full RDP disconnect** (vs. a minimized/backgrounded local session) locks the session and breaks both capture and input — this is a harder failure mode than window occlusion. **DPI:** the capture/input process must call `SetProcessDpiAwareness(PROCESS_PER_MONITOR_DPI_AWARE)` before any capture or click, or coordinates drift on non-100%-scaled displays; some of PyAutoGUI's own dependencies call the older `SetProcessDpiAware()` on import as a side effect, which is one more reason `pydirectinput` (used standalone, no PyAutoGUI import) was preferred over layering PyAutoGUI's mouse acceptance fix on top of it.
- **Fit for our constraints:** Matches the existing "never bake in a resolution" discipline — window size/client-area must be read live, not assumed, exactly like the frame-selection and localization stages already do for recorded video. Working exploration scripts live in the gitignored `scrap_scripts/python/` (`01` capture test, `02` click test, `03` launcher, `04` single-frame grab, `05` frame-space click) with a first 48-frame live collection session (38 clean / 10 tutorial-tagged; 7 distinct roles observed: Gemcrafter, Lover, Confessor, Hunter, Enlightened, Medium, Minion) at `scrap_scripts/python/out/collect_01/` (with an `actions.md` inventory) — candidates for `utils/` promotion under a future `PLAN-live-capture` once a consumer depends on them (Rule 1 promotion trigger not yet met).
- **Addendum — empirical pipeline eval on live frames, 2026-07-29 (same day):** Running the full detection pipeline (not just capture/input) over `collect_01`'s 48 frames — 4 arms, {raw, title-bar-cropped} × {classical, embedding}, via `scrap_scripts/python/07_eval_collect01.py`, artifacts in `scrap_scripts/python/out/eval_01/` — surfaced caveats worth carrying forward beyond the capture/input findings above. Full writeup in DEV-LOG.md (2026-07-29, "First live-frame pipeline eval"); summary here: **(1) status-overlay corruption of identification** — post-execution status icons (dead/skull, etc.) drawn over a card corrupt the crop enough to misidentify the underlying role, including one high-confidence wrong read (revealed Minion → "Hunter" @0.80) and one impossible read (dead Medium → "Lilis," a demon role not in that session's deck); this is a distinct failure mode from plain low-confidence/abstention and needs an overlay-robust read strategy, not just better thresholds. **(2) The Stage-0 menu-brightness gate is dead code on this game** — its `brightness > 160` heuristic assumes a bright menu; this game's menus are dark-themed and the gate never fired across 48 frames, silently gating the main menu as "board" instead. **(3) Unsupported-aspect-ratio finding** — the live window during this collection sat at ~1.53–1.60:1 (vs. 1.778:1/16:9 training footage), and a tutorial popup rendered partially **off-screen** during the same collection run, a GUI-scaling symptom consistent with the game not properly supporting arbitrary window ARs. This is not proven to cause the dominant pipeline failures above (which are geometry-independent), but it means some geometry fault at non-16:9 ARs belongs to the game itself, not just our pipeline; 16:9 is the safe supported shape, now reachable directly via the launch flags documented above rather than via post-hoc cropping. **(4) HUD-mask / live-UI mismatch** — the existing top-9% Stage-1 mask, sized against the recorded footage's HUD, sits above the live game's on-screen objective text ("Find and Execute N Evil..."), which then gets misdetected as a card and misidentified as "Hunter" (0.42–0.50 confidence) in 57% of board frames; this is a mask-sizing problem, not a title-bar-chrome problem (raw vs. cropped arms were byte-identical on the gate). Positive result worth keeping: timing is comfortably real-time on CPU alone (classical ~21–22 ms/frame, embedding ~31–32 ms/frame), so none of the above is a compute-budget concern.
- **Addendum 2 — second eval at supported 16:9 geometry, larger/more-diverse sample, 2026-07-29 (same day):** A follow-up 99-frame session at the now-verified true borderless 1280×720 (`collect_02`, 16 distinct roles, via `scrap_scripts/python/08_eval_collect02.py`, artifacts in `.../out/eval_02/`) held the AR fix from Addendum 1 constant and varied content diversity instead. Headline: fixing geometry did not move the dominant failure modes — content diversity is what surfaced them at scale. Full numbers in DEV-LOG.md (2026-07-29, "Second live eval"); durable caveats worth keeping here: **(1) a Kill-Mode red-tint UI variant is a new identification hazard**, hallucinating up to 5 "Hunter" false positives on a single Hunter-less board (one at 0.93 confidence) — a second, higher-confidence route into the same HUD-text false-positive family documented in Addendum 1; **(2) win/reward/objective/menu/tutorial dialogs are not gate-detected** — 0/6 win dialogs, 0/2 objective dialogs, 0/2 menus, 0/2 tutorial popups were correctly excluded from the board path, only deck overlays gate reliably; **(3) the in-game Compendium is spoiler-gated** (only shows roles already encountered in a town), so it is a post-hoc cataloging aid, not a shortcut to observing all 44 roster roles directly; **(4) classical/embedding complementarity is a real architectural lead, not noise** — on this session's new roles, classical alone got Wretch+Jester, embedding alone got Judge+Slayer, and an ensemble would have covered 5/8 new-role IDs vs. 2/8 for either alone.

## Temporal aggregation of per-frame CV reads (voting/hysteresis, recency weighting, Bayes filtering — and when tracking is overkill) — 2026-07-28

- **Source:**
  - *A Sliding Window Based Approach With Majority Voting for Online Human Action Recognition using Spatial Temporal Graph Convolutional Neural Networks* — ICMLT 2022 (ACM) — https://dl.acm.org/doi/10.1145/3529399.3529425 (open version: https://hal.science/hal-03998451/)
  - Hyndman & Athanasopoulos, *Forecasting: Principles and Practice* (3rd ed.), ch. 8 *Exponential smoothing* — https://otexts.com/fpp3/expsmooth.html
  - Murphy et al., *State Space Models: A Modern Approach* — *HMM filtering (forwards algorithm)* — https://probml.github.io/ssm-book/chapters/hmm/hmm_filter.html ; Labbe, *Kalman and Bayesian Filters in Python*, discrete-Bayes chapter — https://rlabbe.github.io/blog/2016/02/16/discrete-bayes-filter/ (book repo: https://github.com/rlabbe/Kalman-and-Bayesian-Filters-in-Python)
  - Bewley et al., *Simple Online and Realtime Tracking* (SORT) — ICIP 2016 — https://arxiv.org/abs/1602.00763 ; reference code (`max_age`, `time_since_update`) — https://github.com/abewley/sort ; Ultralytics tracker-selection guidance for static cameras — https://docs.ultralytics.com/modes/track
  - Tokmakov, Li, Burgard, Gaidon, *Learning to Track with Object Permanence* — ICCV 2021 — https://openaccess.thecvf.com/content/ICCV2021/papers/Tokmakov_Learning_To_Track_With_Object_Permanence_ICCV_2021_paper.pdf
- **Authority / trust:** **A** for FPP3 (standard forecasting textbook), the SSM book (recognized authority — Murphy et al., with runnable code), SORT (peer-reviewed ICIP paper + canonical reference implementation), and Tokmakov et al. (ICCV). **A/B** for the ICMLT sliding-window paper (peer-reviewed, but a minor venue — used as a representative of a very common pattern, not as the pattern's origin). **B** for Labbe (widely-used open engineering textbook with code, not peer-reviewed) and the Ultralytics docs (official vendor docs; guidance, not measurement).
- **Reason for inclusion / what we were looking for:** Stage 4 must merge per-card reads **across frames**: identity flicker between frames, modal frames where the board is hidden, and cards that reveal over time (face-down → face-up). We needed the standard options for temporally aggregating noisy discrete per-frame classifications, and evidence on whether full multi-object tracking is warranted when the objects sit in **fixed slots**.
- **Abstract of findings:** Four escalating families, plus one negative result. **(a) Sliding-window majority vote** is the standard cheap post-processing for noisy per-frame labels (the ICMLT paper applies exactly this to per-frame action classifications; the same pattern recurs across the action-recognition literature): take the modal label over the last *N* frames. Its documented cost is **latency — a real change needs ~N/2 agreeing frames to win the vote**, so window size is a direct stability-vs-lag dial; the hysteresis variant (switch the reported label only after *k* consecutive frames disagree with the held label) is the debounce formulation of the same idea. **(b) Exponential smoothing** (FPP3 ch. 8) replaces the hard window with recency weights that decay geometrically — one parameter (α), O(1) memory per tracked quantity, no window buffer; applied to a per-class belief vector it smooths flicker while responding faster to sustained change than an equal-weight window of similar effective length. FPP3's framing is forecasting, not vision — the transfer is the smoothing machinery, not the use case. **(c) The discrete Bayes filter / HMM forward algorithm** (SSM book; Labbe) is the principled version of (b): a belief over discrete states updated by predict (transition model — e.g. "identity rarely changes; face-down→face-up allowed") and update (observation likelihood) steps; a **missing observation is handled cleanly by skipping the update step**, so occlusion gaps need no special case. Its honest cost: it demands an **observation model — P(observed label | true state)** — and our identifier's confidence is a **top1−top2 cosine margin, not a probability**, so using a Bayes filter properly requires calibrating margin → likelihood on labeled data (which we don't have yet; that is the round-2 dataset-building dependency). Uncalibrated, the filter degenerates into a dressed-up weighted vote. **(d) Full multi-object tracking is not warranted for fixed slots.** MOT machinery (Kalman motion models, Hungarian association, re-ID) exists to solve **data association under motion** — SORT's own finding is that with association solved, detection quality dominates and the tracker itself can be minimal; Ultralytics' guidance for static cameras is likewise "minimum tracker overhead." Our cards sit in fixed board slots localized per frame by layout, so association is **deterministic by slot index** — the "tracking" problem degenerates to K independent per-slot label filters, i.e. family (a)–(c). **(e) Occlusion handling in production trackers** is state-hold plus a staleness counter: SORT keeps `time_since_update` per track, coasts through gaps, and deletes after `max_age`; the object-permanence literature (Tokmakov et al.; follow-on work) argues for holding hypotheses through occlusion but warns that long-held state goes **stale** (false persistence). For fixed slots the deletion half is wrong (the slot doesn't leave the scene) — the transferable pattern is **hold last confirmed state + expose the staleness explicitly** rather than silently serving old reads as fresh.
- **Fit for our constraints:** All of (a)–(c) are a few lines of numpy per slot — trivially within the mid-grade-PC budget; MOT frameworks would add dependency weight for an association problem we don't have (fixed slots), so (d) rules them out. The margin-not-probability semantics of `classify_crop_embedding` fits a **margin-weighted vote** naturally (margin = decisiveness = vote weight; abstentions vote nothing) without any calibration step; a discrete Bayes filter is the *teachable* principled endpoint but is only honest once margins are calibrated to likelihoods on labeled board crops. Face-down→face-up reveals are a near-one-way transition — a latch/hysteresis (an identity, once confidently established, needs strong contrary evidence to flip) encodes it in any of the three families. Modal frames = missing observations: hold per-slot state, count staleness, surface it in the schema (the SORT `time_since_update` pattern, minus deletion). Options and the REST-contract implications are laid out in `plans/PLAN-temporal-assembly.md`.

## Brightness/luminance-statistic heuristics for frame-state gating (center-vs-ring ratio) — 2026-07-28 *(retroactive — technique shipped 2026-06-22; logged during audit remediation. The research-before-deciding rule was violated for this technique; this entry closes the record.)*

- **Source:**
  - *Video shot-boundary detection: issues, challenges and solutions* — Artificial Intelligence Review (Springer, 2024) — https://link.springer.com/article/10.1007/s10462-024-10742-1
  - *Shot Boundary Detection: Fundamental Concepts and Survey* — CEUR-WS Vol. 2589 — https://ceur-ws.org/Vol-2589/Paper6.pdf
- **Authority / trust:** **A** for the Springer survey (peer-reviewed journal); **B** for the CEUR workshop survey (workshop-reviewed, standard reference material). Neither addresses game-UI state detection specifically — they establish the legitimacy of the *family* (cheap luminance/intensity statistics for frame classification), not our exact gate.
- **Reason for inclusion / what we were looking for:** Retroactive grounding for the Stage 0 frame-state gate (`src/dbcv/frame_state.py`): classifying a frame as board / modal / menu from a **center-vs-ring mean-brightness ratio**.
- **Abstract of findings:** The shot-boundary/frame-filtering literature's cheapest tier is exactly this family: pixel-intensity and luminance-histogram statistics compared against thresholds, valued for an "acceptable trade-off between computational complexity and performance." Its documented weaknesses transfer to us: absolute-intensity measures are "very sensitive to luminance changes," and global histograms ignore spatial layout, so dissimilar content can alias. Both weaknesses showed up in practice — absolute center brightness scored 0/3 on modal frames (modals share the board's dark starfield) — and the fix was spatially-structured statistics: the **ratio** of center-region to surrounding-ring brightness (board ~1.0–1.1, modal ~3–6; threshold 2.0 in a clean 3× gap; 7/7 labelled frames correct).
- **Fit for our constraints (and the honest record):** The original frame-selection entry (2026-06-21) recommended **template-matching on stable UI anchors** for this gate. The shipped gate is the cheaper brightness heuristic instead, adopted because it went 7/7 on the labelled frames with zero dependencies beyond numpy and no anchor templates to maintain across art swaps. The anchor/template approach **remains the documented fallback** if the ratio gate over- or under-fires on new modal types (`Sample1_000` is already the closest call at 3.1 vs threshold 2.0).

## Color-histogram matching for object identification (HSV histogram + correlation metric) — 2026-07-28 *(retroactive — technique shipped 2026-06-22; logged during audit remediation. The research-before-deciding rule was violated for this technique; this entry closes the record.)*

- **Source:**
  - Swain & Ballard, *Color Indexing* — IJCV 7(1):11–32, 1991 — http://www.liralab.it/teaching/SINA/slides-current/swain.ballard.1991.pdf
  - OpenCV *Histogram Comparison* tutorial (`cv::compareHist`, `HISTCMP_CORREL`) — https://docs.opencv.org/4.x/d8/dc8/tutorial_histogram_comparison.html
- **Authority / trust:** **A** — the canonical peer-reviewed anchor for histogram-based object identification (verified: IJCV vol. 7 no. 1, 1991), plus official OpenCV documentation for the exact function/metric used.
- **Reason for inclusion / what we were looking for:** Retroactive grounding for the classical Stage 2 identifier's primary signal (`src/dbcv/identify.py`): matching a card crop against the reference gallery by **2-D HSV (hue×sat) histogram correlation**.
- **Abstract of findings:** Swain & Ballard established that color histograms of multicolored objects are a robust, efficient index into a database of models — stable over viewpoint change and able to differentiate many objects (66-model dataset: correct model was the best match 29/32, second-best the other 3). Their matcher is **histogram intersection**; OpenCV's `HISTCMP_CORREL` is a different metric from the same family (Pearson correlation over bins, higher = better, 1.0 = identical), documented officially. Honest caveats: histograms discard spatial layout (two different cards with similar palettes alias — observed as a duplicate-`Scout` false match), and the correlation metric degenerates on all-zero input (`compareHist(zeros, ·) == 1.0` — hit in practice, fixed with a zero-sum guard).
- **Fit for our constraints:** Value channel excluded from the histogram to survive state-tinting; opencv-only, zero training, gallery rebuild = art-swap story. Measured ~40–60% on face-up cards with honest "unknown" elsewhere — kept as the conservative fallback identifier and the pedagogical lower bound (Module 05).

## ORB features + Lowe ratio test as an identification tiebreaker — 2026-07-28 *(retroactive — technique shipped 2026-06-22; logged during audit remediation. The research-before-deciding rule was violated for this technique; this entry closes the record.)*

- **Source:**
  - Rublee, Rabaud, Konolige, Bradski, *ORB: an efficient alternative to SIFT or SURF* — ICCV 2011 — https://sites.cc.gatech.edu/classes/AY2024/cs4475_summer/images/ORB_an_efficient_alternative_to_SIFT_or_SURF.pdf
  - Lowe, *Distinctive Image Features from Scale-Invariant Keypoints* — IJCV 60(2):91–110, 2004 — https://www.cs.ubc.ca/~lowe/papers/ijcv04.pdf
- **Authority / trust:** **A** — both canonical peer-reviewed papers (ICCV 2011; IJCV 2004), verified. Cross-reference: ORB was previously cited in this file only under the **localization** entry (2026-06-21, via a B/C-tier practitioner SIFT-vs-ORB comparison); this entry anchors its **identification** use to the primary sources.
- **Reason for inclusion / what we were looking for:** Retroactive grounding for the classical Stage 2 identifier's tiebreaker (`src/dbcv/identify.py`): when the top-2 histogram correlations are within 0.05, ORB keypoint matching decides.
- **Abstract of findings:** ORB (oriented FAST keypoints + rotated BRIEF binary descriptors) performs comparably to SIFT in many matching tasks at roughly two orders of magnitude less cost, and is patent-free — the right local-feature choice for a CPU-budget pipeline. Lowe's ratio test (IJCV 2004, §7.1) filters matches by the ratio of nearest to second-nearest descriptor distance; at his 0.8 threshold it eliminated ~90% of false matches while discarding <5% of correct ones. Honest caveats: binary-descriptor matching is weaker than SIFT under large scale change, and stylised flat card art yields fewer distinctive keypoints than the textured photos the papers benchmark on — which is why ORB is a *tiebreaker* here, not the primary signal.
- **Fit for our constraints:** opencv-built-in, no model, no training, negligible latency on ~2 candidate comparisons per crop; re-fits on an art swap with the gallery rebuild alone.

## Why a frozen-ImageNet embedding + NN gallery collapses on stylized cards, and how to fix it — 2026-06-22

- **Source:**
  1. Chen, Liu, Kira, Wang, Huang, *A Closer Look at Few-Shot Classification* (ICLR 2019) — https://openreview.net/pdf?id=HkxLXnAcFQ
  2. Kumar, Raghunathan, Jones, Ma, Liang, *Fine-Tuning can Distort Pretrained Features and Underperform Out-of-Distribution* (ICLR 2022, oral) — https://arxiv.org/abs/2202.10054
  3. Salvador & Oberman, *ImageNet-Cartoon and ImageNet-Drawing: two domain shift datasets for ImageNet* (ICML 2022 "Shift Happens" workshop) — https://tiagosalvador.github.io/projects/imagenet-shift/ ; code https://github.com/oberman-lab/imagenet-shift ; with Li et al., *Deeper, Broader and Artier Domain Generalization* (PACS, ICCV 2017) — https://arxiv.org/pdf/1710.03077
  4. Kim, Kim, Cho, Kwak, *Proxy Anchor Loss for Deep Metric Learning* (CVPR 2020) — https://arxiv.org/pdf/2003.13911 ; Musgrave et al., *PyTorch Metric Learning* (official docs, loss catalog incl. ArcFace/CosFace/SubCenterArcFace/SupCon/ProxyNCA/ProxyAnchor) — https://kevinmusgrave.github.io/pytorch-metric-learning/losses/
  5. Kornblith, Shlens, Le, *Do Better ImageNet Models Transfer Better?* (CVPR 2019) — https://arxiv.org/pdf/1805.08974 ; Cubuk et al., *RandAugment* (NeurIPS 2020) — https://arxiv.org/pdf/1909.13719
- **Authority / trust:** **A** for 1, 2, 3-PACS, 4-ProxyAnchor, 5 (all peer-reviewed CVPR/ICCV/ICLR/NeurIPS papers); **A** for the pytorch-metric-learning docs (official, actively maintained library) and the ImageNet-Cartoon/Drawing workshop paper + code (recognized authors, public benchmark). Loss head-to-head "which wins" claims from non-peer-reviewed comparisons (arXiv 2601.21450, 2503.13045) were treated as **B/C** leads only and are *not* relied on for the ranking — the canonical primary papers are.
- **Reason for inclusion / what we were looking for:** Diagnosing — and naming — a concrete, observed failure of our Stage-3 identifier: a **frozen ImageNet-pretrained MobileNetV3-Small** backbone + **cosine NN over per-class mean ("prototype") embeddings** for 43 stylized Demon Bluff card characters. The embeddings collapse (inter-prototype cosine 0.65–0.94), so it names ~100% of slots with poor precision (over-identifies), and a conservative classical HSV+ORB matcher beats it by honestly returning "unknown." We needed to know whether this is a known phenomenon, what fixes the literature recommends, and which fix fits our budget first.
- **Abstract of findings:** This is a **known, well-documented failure**, and the correct name is **domain shift / domain gap of frozen ImageNet features to a stylized (cartoon/illustration) domain compounded by fine-grained similarity** — *not* "neural collapse." (Neural collapse is a distinct training-dynamics phenomenon where a model's *own* trained class means converge to an equiangular tight frame on its *in-distribution* training data; it is not what describes generic frozen features failing to separate an unseen out-of-distribution class set, so that framing is refuted here.) Three primary results pin the diagnosis: (3) **ImageNet-pretrained accuracy "decreases significantly"** when the same images are rendered as cartoons/colored-pencil drawings (ImageNet-Cartoon/-Drawing), and the **PACS** Photo→Art/Cartoon/Sketch benchmark shows large accuracy drops across the photo→illustration gap — i.e. natural-image features genuinely do not transfer to stylized art off the shelf; (5) Kornblith et al. find ImageNet-accuracy↔transfer correlation **breaks down on fine-grained datasets**, where pretrained features give little benefit because the discriminative cues are subclass-specific, not generic — exactly our 43 visually-similar characters; (1) **Chen et al.'s keystone result**: a *simple cosine-distance classifier on a frozen backbone* (their "Baseline++") is competitive with ProtoNet/MatchingNet **only when base and novel classes share a domain** — under a **domain shift between base and novel classes the advantage of the prototypical/meta-learning machinery disappears, and the limiting factor becomes the backbone's features, not the classifier head.** Our gallery-of-prototypes *is* Baseline++/ProtoNet inference, and we are squarely in the domain-shift regime, so no amount of better distance metric or fancier few-shot head will rescue frozen features — **the features must be adapted.** On *how* to adapt under a tiny dataset: (2) Kumar et al. (ICLR'22 oral) show full fine-tuning can **distort** good pretrained features and underperform out-of-distribution (they report ~2% higher in-distribution but ~7% lower OOD vs linear probing), and that the two-stage **LP-FT (linear-probe **then** fine-tune)** beats both (≈+1% ID, ≈+10% OOD over full FT) because warming up the head first means fine-tuning perturbs the trunk less; the broader small-data literature concurs that **full fine-tune overfits on <~10³ examples** while head-only is stable but capacity-limited — motivating **partial unfreeze (top blocks) or LP-FT** as the middle path. On the loss: metric-learning losses that impose **angular margin (ArcFace/CosFace)** or **proxy structure (ProxyNCA/Proxy-Anchor)** directly attack inter-class collapse by enforcing a cosine margin between classes; (4) **Proxy-Anchor** specifically targets our pain points — it converges **fast**, is **robust to label noise/outliers**, avoids O(n²) pair/triplet mining, and works with **few examples per class** (each class compared to one learnable proxy), which is the natural training-time analogue of our inference-time prototype gallery. On augmentation: when you start from a handful of clean reference crops, **strong augmentation pays its largest dividend** (it is the canonical small-data regularizer); **RandAugment** (one magnitude knob, N≈2/M≈9 as a starting point, tuned on a held-out fold) plus the geometric/photometric perturbations that mimic our real capture variation (small rotation/scale/translation, brightness/contrast/JPEG/blur) is the standard recipe, combined with weight decay + early stopping. **Caveats / honest counter-arguments:** (a) ArcFace/CosFace are reported to **underperform when intra-class statistics are near-collapsed or classes have ~1 example**, so an angular-margin softmax is *not* an automatic win at our extreme low-shot end — proxy-based or supervised-contrastive losses degrade more gracefully there; (b) Kornblith et al. also note that for some targets a *from-scratch* small net rivals fine-tuning given enough data — not our case (we have 1–67 images), which is exactly why we lean on pretraining + adaptation rather than training a backbone from zero; (c) the single most important honest point: our prototypical framing was never wrong as an *inference* structure — it failed only because the *features feeding it* are un-adapted, so the fix is feature adaptation, not abandoning the gallery.
- **Fit for our constraints (the recommended approach):** Constraints recap — 1–67 reference images/class × 43 classes, train on one **Titan Xp (12 GB, Pascal sm_61, FP32 only)**, runtime **≤~30M params / ≤~100MB**, served **ONNX on CPU**. **Round 1 (reach for first): fine-tune the SAME MobileNetV3-Small backbone with an angular-margin / proxy metric-learning loss, unfreezing only the top block(s) via LP-FT, with strong augmentation; keep the cosine-NN prototype gallery unchanged at inference.** Justifications, one line each: *Loss* — **Proxy-Anchor** (or ArcFace if classes prove well-populated) directly enforces an inter-class cosine margin, which is precisely the collapse we measured, and Proxy-Anchor converges fast and tolerates ~few-shot classes; *Unfreeze depth* — **LP-FT / top-block partial unfreeze**, because full fine-tune overfits and *distorts* features on <10³ images (Kumar et al.) while head-only can't close a domain gap (Chen et al.) — the middle path is the documented sweet spot; *Augmentation* — **RandAugment (N≈2, M≈9) + capture-realistic geometric/photometric jitter**, the canonical highest-payoff regularizer when starting from few clean references; *Runtime* — MobileNetV3-Small stays ~2.5M params / <8MB, so fine-tuning changes **zero** about the ONNX-on-CPU serving path or the budget, and an art swap re-fits cheaply on the Titan Xp. **Keep the conservative HSV+ORB matcher's "unknown" behavior** — port an abstention threshold (min cosine margin to top-1) onto the embedding head so the learned model can also say "unknown" instead of over-identifying. **Round 2 (if Round 1 underperforms): switch the loss to supervised-contrastive (SupCon) and/or go to a deeper partial unfreeze or a slightly larger backbone (still ≤30M / ≤100MB), and add class-balancing for the long tail (1 vs 67 images).** Justification — SupCon/contrastive degrade more gracefully than angular-margin at the extreme low-shot end and use multiple positives per class; a deeper unfreeze buys more domain adaptation once the head is warm; class-balanced sampling/loss counters the 1–67 imbalance. *(Note for the lesson plan: this is a teachable arc — the classical conservative baseline beating a naive deep model, the correct diagnosis as domain-shift-not-neural-collapse, and the principled fix being feature adaptation under a tiny-data discipline.)*

- **Abstract of findings:** `venv` (stdlib since Python 3.3) creates an isolated directory with a private `site-packages` and a `python`/`pip` pointing into it; it does not install packages or manage interpreter versions. `pip` (bundled since Python 3.4) installs packages from PyPI into a target environment; a pinned `requirements.txt` (`package==x.y.z`) is the minimal reproducibility mechanism. `virtualenv` is the third-party predecessor to `venv`; it adds faster env creation and broader configuration but is rarely needed directly on modern Python 3. `conda` (Anaconda/Miniconda/miniforge) manages environments *and* installs packages including non-Python native binaries (CUDA, BLAS, MKL); it is not Python-specific, operates on its own channel ecosystem (conda-forge), and provides pre-built binaries for a wider platform matrix than PyPI wheels — but mixing conda and pip installs into the same environment is a documented source of dependency corruption. `uv` (Astral, 2024+) reimplements pip + venv in Rust; per its documentation it installs packages significantly faster than pip via aggressive caching and parallel downloads; it also produces `uv.lock` lockfiles pinning all transitive dependencies, and newer versions manage Python interpreter versions. `uv` is pip-compatible (reads `requirements.txt`, `pyproject.toml`) but is a separate installation step not bundled with Python. Caveats: `conda` and `pip` should not be mixed in the same environment without care; `uv` does not manage non-Python system libraries the way conda does; no vendor speed claims are cited as numbers here because figures vary substantially across machine configurations and cache states.
- **Fit for our constraints:** The project chose `venv` + pinned `requirements.txt` as the zero-install, universally reproducible baseline — every Python ships `venv`, every learner can follow along without first installing a tool. `uv` (speed) and `conda` (native binary stacks) are taught as alternatives in Module 00 of the lesson plan, with honest tradeoffs. `opencv-python-headless` (not `opencv-python`) is used because the pipeline is server/batch — no GUI, no GTK/Qt dependency. Packages not yet justified by research are consciously deferred from `requirements.txt` (conservative path: onnxruntime, torch, imagehash held back until a pipeline stage warrants them).

(3) Scene-cut detection only flags *that* something changed, not *whether a board is on screen* — a separate cheap board-gate is still needed.

## Card identification that is cheap to retrain when art changes — 2026-06-21

  2. Wu, Efros, Yu, *Improving Generalization via Scalable Neighborhood Component Analysis* (ECCV 2018) — https://arxiv.org/pdf/1808.04699 (softmax classifier vs. NN retrieval over learned embeddings)
  3. Howard et al., *Searching for MobileNetV3* (ICCV 2019) — https://openaccess.thecvf.com/content_ICCV_2019/papers/Howard_Searching_for_MobileNetV3_ICCV_2019_paper.pdf
  4. *Limitations of Template Matching* — https://apxml.com/courses/introduction-to-computer-vision/chapter-5-introduction-object-recognition/limitations-template-matching ; survey arXiv:1610.07231 — https://arxiv.org/pdf/1610.07231
  5. LanceDB, *Zero-Shot Image Classification with Vector Search* (2024) — https://lancedb.com/blog/zero-shot-image-classification-with-vector-search/
- **Authority / trust:** **A** for 1–3 (canonical NeurIPS/ECCV/ICCV papers). **B** for 4 (survey [A] + teaching page [B]) and 5 (vendor engineering blog with working code; promotional framing).
- **Reason for inclusion / what we were looking for:** Naming each localized card (~44 roles + role class) in a way that is cheap to re-fit when the art set changes — the *retrain cost* on an art swap is the central question.
- **Abstract of findings:** The four families split cleanly on retrain cost. **(a) Template matching / NCC** needs zero training (swap the reference template) but degrades with even small rotation, scale, illumination, occlusion, or deformation; wants one template per *appearance*. **(b) Embedding similarity / metric learning** (small backbone — MobileNetV3-Small / small ResNet / frozen CLIP — + nearest-neighbor over a reference gallery) is the sweet spot: on an art swap you re-embed the new references and change *no weights*; Wu et al. show NN retrieval can *beat* a softmax classifier and is more interpretable. **(c) Few-shot / prototypical networks** formalize this — each class is the mean of a few embedded supports, new classes added at inference with *no parameter updates*. **(d) A small trained CNN classifier** is cheapest at inference and most accurate *for its training art*, but is the only family that must be **relabeled and retrained** on an art swap. Caveats: (b)/(c) push cost to inference (trivial at ~44 classes); a *frozen generic* backbone may underperform on stylized art without light adaptation. Honest counter-argument: at ~44 well-localized frontal crops, even template matching or a tiny classifier may hit high accuracy — the embedding/few-shot machinery earns its keep specifically because of the *art-swap constraint*.
- **Fit for our constraints:** Recommend **(b) a small frozen embedding backbone + nearest-neighbor over a per-art reference gallery**, collapsing to **(c) prototypical** by averaging a few references per card. On an art swap, (a)/(b)/(c) need **only the new reference images and zero gradient steps** — re-embed ~44 cards in seconds — whereas **(d) requires re-cropping, relabeling, retraining**. The backbone fits easily on Titan XP/Colab (or off-the-shelf); inference is one forward pass + a 44-way distance compare (negligible on a mid-grade PC). Pragmatic hybrid for the course: keep an **NCC/template fast-path** for clean axis-aligned crops (teaches the classical baseline, free to re-fit), fall back to **embedding-NN** for ambiguous cards, and frame the trained classifier as the approach we *reject* for production because of its retrain cost. *(Sample frames confirm a second identity signal: a name-label text under each card — OCR can corroborate the visual match; see the OCR entry.)*

- **Abstract of findings:** A small detector is effectively free at runtime: **YOLO11n = 2.6 M params / 6.5 BFLOPs, ~1.5 ms on T4 (TensorRT)**, YOLOv8n **~1.76 ms on an RTX 3060** (500+ FPS headroom); on CPU YOLO11n ~56 ms (~18 FPS), nano/tiny 20–30 FPS on a 6-core CPU. Small classifiers are smaller: **MobileNetV3-Small 2.5 M params, <8 MB, ~13 ms CPU**; **ResNet18 11.2 M params, ~43 MB, ~14 ms CPU**. Mobile OCR (~8 MB) is the heaviest per-call item (~420 ms CPU / ~140 ms T4 per crop) → run only on selected regions. The hard ceiling is **dev/labeling-only** foundation models: **SAM ViT-H 632 M params**; **Grounding-DINO "too slow for real-time even on A100."** Caveats: **INT8 helps mainly on CPU** (x86 VNNI); on GPU it **needs Tensor Cores (T4/A100)** — the **Titan Xp/Pascal has none and runs FP16 at ~1/64 FP32**, so keep dev work FP32. A custom YOLOv8 fine-tune is **~2.5 h on a free Colab T4**; small models fit the Titan Xp's 12 GB in FP32 (slower than Ampere, no mixed precision).
- **Fit for our constraints:** **Runtime (ship): YOLOv8n/YOLO11n nano-detector class (≤~3 M params, ≤~10 BFLOPs) and MobileNetV3-Small/ResNet18-class classifiers (≤~12 M params, ≤~45 MB)** — real-time on a 3060 with margin, 10–30 FPS on CPU fallback; mobile-OCR (~8 MB) fine **if gated to detected text regions**. Rule of thumb: **≤~30 M params / ≤~100 MB ≈ comfortably real-time on a mid-grade GPU**; reserve large ViT / SAM (600 M+) / Grounding-DINO strictly for **dev-only** dataset labeling. Train custom runtime models **FP32, ≤12 GB**: the nano-detector + small-classifier recipe trains in a few hours on a free Colab T4 (feasible if slower on Titan Xp), satisfying "cheap to retrain on art swap" — but don't rely on mixed-precision/INT8 speedups on Pascal.
