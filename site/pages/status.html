Project status & handoff summary

Where the pipeline and the course stand right now, in plain terms — a snapshot for picking the work back up. The cited, authoritative version lives in the repo docs (linked at the bottom).

One line: the pipeline already reads a Demon Bluff board end-to-end from a single frame — it finds the cards, decides whether the frame even shows a board, takes a first pass at naming each card, and serves the result as JSON over HTTP. Everything runs on CPU; the heavier tools are dev-only.

What's working

End-to-end path (per frame): frame → state gate (board / modal / menu) → localization (find the card slots) → identification (name each card) → assembly → a versioned GameStateSnapshot → POST /v1/snapshot. There's also a command-line runner that does the same on saved frames and draws annotated overlays.

  • Frame-state gate. Tells a real board from a menu or a pop-up dialog by comparing the brightness of the centre to the ring around it — the trick is that the game's dialogs sit on the same dark background as the board, so plain brightness fails but the ratio separates them cleanly.
  • Localization (classical, no trained detector). Finds the cards by colour + shape geometry rather than a learned model — 8 / 8 and 9 / 9 cards exact on clean board frames, and it survives an art swap by re-tuning, not retraining.
  • Identification (two approaches, honest results — see below).
  • REST service. FastAPI; models load once at startup; CPU-bound work runs off the event loop; the JSON snapshot is versioned and always reports the resolution it actually measured (never a hard-coded size).
  • Tests: 81 passing in about 22 seconds.

The honest finding (identification)

This is the kind of real result the course exists to show. Two identifiers were built:

  • Classical (colour-histogram + feature match against a reference gallery): roughly 40–60% correct on face-up cards, and correctly says "unknown" on face-down cards (a blank card back matches nothing — the right answer).
  • Embedding nearest-neighbour (a small image model → vector → nearest gallery vector): the architecture is the production-intended one and re-fits on an art swap with zero training. But the off-the-shelf (frozen, photo-trained) model squashes all the cartoon characters into one tight cluster, so it confidently names nearly every slot — without being more accurate than the conservative classical method.

The takeaway, which becomes a lesson: an embedding model doesn't magically win — you have to adapt it to your domain. The next step is a light fine-tune of that model on card crops, which the dev machine can now do locally. Until then the conservative classical identifier is the safer default for an API (an honest "unknown" beats a confident wrong answer).

The course (the real deliverable)

The lesson plan is the primary product; the pipeline is its worked example. 8 of 10 modules are drafted, each anchored to a real decision made while building: environments, framing, frame selection, resolution-agnostic geometry, localization, identification, REST serving, and staying-alive (keeping a recognizer working when the art changes). The two not yet written — on-card text reading and multi-frame state assembly — wait on the pipeline stages they describe.

How it's built

  • Environment: a project-local virtual environment with pinned dependencies (the course also teaches the trade-offs between venv/pip, conda, and uv).
  • Classical CV: OpenCV (headless) + NumPy — the localization and the first identifier.
  • Serving: FastAPI + ONNX Runtime on CPU; small models only, no batching.
  • Dev-time ML: PyTorch (GPU) is used only to prepare/export models, which are then served on CPU. Runtime models stay small enough for a mid-grade gaming PC.

What's next

  • Fine-tune the embedding model on card crops, re-export, and re-measure against the classical baseline.
  • On-card / HUD text reading (a tiny recognizer for the small, fixed set of words and numbers).
  • Combine reads across several frames into one stable snapshot (single frames can be occluded by dialogs).
  • Finish frame selection (skip-ahead decoding + dropping near-duplicate frames) and the remaining two lesson modules.
